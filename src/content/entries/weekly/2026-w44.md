## AI Native work calls for cross-disciplinary knowledge

[Manus Zhang Tao's thoughts on AI Native transformation](https://mp.weixin.qq.com/s/I_hNNAf7LFBf5nJ0rEJHig?scene=1) show that product managers and designers have started using AI to take a product from end to end. This lowers the coordination and communication costs between departments, which makes cross-disciplinary knowledge important.

## Treat AI as a collaborator

[How to Be More Ambitious: A Tutorial for Humans with Models](https://felixrieseberg.com/how-to-be-more-ambitious-a-tutorial-for-humans-with-models/) presents a way of working with AI: treat it as a collaborator rather than a simple tool. Give it a goal that seems impossible, make the standard for the result concrete, ask it to think like a professional, and use the process to expand your own knowledge.

## Waza's engineering experience

[tw93/Waza](https://github.com/tw93/Waza) collects tw93's engineering experience.

### /think states a position before writing code

The first constraint in `/think` is that it cannot write code before the user approves. It requires the AI to state a position and identify what evidence would change it. It also rules out evasive language such as “this is interesting.”

It produces an Outcome Contract. The goal, success criteria, constraints, selected approach, rejected tradeoffs, tests, and handoff steps must be specific enough to execute without another round of decisions.

Its Durable Context Preflight reads only the domain rules relevant to the question before producing a plan. It does not load the entire rule tree. If a plan conflicts with a hard project rule, the AI states in one sentence which rule conflicts with which step and proposes a resolution. It never silently overrides the rule. If a rule blocks the plan, it stops and asks the user.

`/think` has three modes:

- **Lightweight Mode** gives a recommended fix in two or three sentences, lists the files involved and one risk, then waits for approval before implementation. It upgrades to the full mode when there are more than two genuinely distinct options with material tradeoffs.
- **Evaluation Mode** handles a single value judgment such as whether something is worth doing or should be kept.
- **Triage Mode** handles a bundle of independent requests or screenshots in an itemized table, rather than forcing them into one conclusion.

### /design makes the design direction concrete

The first rule of `/design` is that a result is not specific enough if a default prompt could produce it.

Before writing code, it directly asks five questions: who will use the product and in what situation; what precise aesthetic direction to pursue, such as dense editorial, native terminal, ink on paper, brutalist grid, or warm analog, rather than “clean and modern”; one thing users should remember, such as typography, a color system, an unexpected motion, or an asymmetric layout; hard constraints such as framework, bundle size, minimum contrast, and keyboard accessibility; and a signature microinteraction, such as press scaling, staggered reveals, or contextual icon animation, including exactly how it will be implemented. It does not continue until all five questions have answers.

When a user provides references such as Linear, Claude.ai, or Vercel, `/design` does not use the brand name as the direction. It extracts three concrete attributes: the button corner-radius approach; surface depth through shadows, background levels, or borders; and the accent-color family.

It then summarizes the direction in three lines: a visual thesis covering mood, material, and energy; a content plan with one sentence each for the hero, supporting content, details, and final CTA; and an interaction thesis with two or three specific motions that change how the page feels. Production or multi-page UI work expands this into a nine-section `DESIGN.md` scaffold covering theme, palette, typography, components, layout, depth, do/don't, responsiveness, and prompting guidance.

Non-negotiable constraints come from the loaded reference files. They cover typography, OKLCH color, motion timing, layout defaults, forbidden CSS patterns, accessibility baselines, and complexity matching. The AI follows them without repeating the entire rule set in its main instructions.

### /ui iterates on existing interfaces from screenshots

`/ui` is for screenshot-driven iteration when an existing interface has visual problems. It preserves the user's diagnostic words, such as “ugly,” “messy,” “unclear,” or “weird,” rather than translating them into a vague request to make things modern.

It maintains a Reflex Fonts to Reject list that includes Inter and DM Sans. The restriction targets reflexively using these fonts as display type. A justified use in a specific product interface, such as a dense data table, can still use Inter. The skill also specifies forbidden CSS patterns, animation standards, color systems, and themes.

Containers whose children switch state, such as status bars, action bars, toolbar rows, and menu items, use the same font size in every state. State is shown through fill, stroke, opacity, color, or icons, never through font-size changes.

Outputs from `/ui` cannot use the U+2014 em dash. Use commas, colons, or periods instead. Default palettes, default fonts, and hand-drawn graphics are allowed only when there is no reference. Colors, fonts, widths, and tone come first from the current product's tokens, sibling components, screenshots, and git history, then from other products shipped by the same team.

### /check separates review from write access

`/check` separates a review request from permission to write. Read-only requests can inspect workspace and remote state. Editing files, auto-fixing, committing, pushing, publishing, commenting, closing, merging, or switching branches requires explicit authorization in the current request or valid authorization from the same unfinished task.

“Continue” in the same task preserves authorization and does not require asking again. A new action, wider scope, changed target, or added risk outside the original authorization requires fresh approval. Approval of a draft does not approve committing, pushing, publishing, or deleting.

It produces an Outcome Contract. Review findings, release decisions, and maintainer actions must rely on the current diff, project context, and live evidence. Findings, fixes, published state, and blockers each need proof from commands, artifacts, or remote status. Evidence can come from workspace state, diffs, public project docs, manifests, CI, package contents, release or registry state, and current command output.

Multi-step or release work, and requests containing multiple items or screenshots, end with a numbered ledger of completed, not applicable, and remaining items instead of a narrative summary.

Before any review, it runs `git status --short --branch -uall`. It checks whether workspace drift makes the plan unsafe, names conflicts and stops, then executes and runs the project's validation commands.

### /hunt finds the root cause before a fix

The hard rule in `/hunt` is to leave code untouched until the root cause fits in one sentence. The required form is “I think the root cause is [X], because [evidence],” and it must identify a specific file, function, line, or condition. “A state management problem” is not testable. “The cache in `useUser` at `src/hooks/user.ts:42` expires because the dependency array omits `userId`” is.

It uses diagnostic signals to judge progress: whether a log line matches the hypothesis; whether the next error can be predicted before running; whether the path from cause to symptom is understood; and whether a test can be written that fails on the old code. Each signal needs another independent piece of evidence before it can justify action.

Before acting on a hypothesis, it lists every observable symptom, not only the first one the user reported. A hypothesis must explain all of them. One that covers only part of the symptoms is still a symptom-level guess. Timing-related problems such as flicker, intermittent failures, and race conditions must be reproduced reliably before diagnosis.

It blocks five rationalizations: “I'll just try it” means no hypothesis has been written; “I'm sure” means a proving tool still needs to run; “it's probably the same issue” means rereading the execution path from the beginning; “it works on my machine” means listing environmental differences before dismissing them; and “restart once more” means reading the last error verbatim, with no more than two restarts without new evidence.

If the same symptom remains after a fix, work stops. “Let me try this” also triggers a hard stop. Both mean the hypothesis is unfinished and the execution path must be reread from the beginning.

### /write preserves the author's voice and edits by subtraction

The core stance of `/write` is to remove the performance of improvement instead of upgrading vocabulary. It is a catalog of patterns to notice, not a checklist to apply from top to bottom. Its references are long because they collect examples. Applying more rules does not make the result better.

Over-editing is as bad as under-editing. A sentence that is already natural, clear, and stable stays as it is. Most editing is subtraction: remove repetition, summary tone, and restated conclusions instead of replacing words one by one. Preserve the author's colloquial language, rhythm, knowledge, and position. The author's emotion, stance, and intentional style choices take precedence over an individual rule, including question-form titles in narrative writing or a list the author wants to keep. Banned phrases and replacement tables are examples, not find-and-replace instructions. A phrase on a list stays when it reads naturally in context. Match the pattern, not the string. Three meaningful edits are better than thirty mechanical changes that flatten the voice.

The preflight locates the text first, then locks the audience, then determines the language. If the user provides only an instruction and no text, it asks for the text in one sentence. For a long article, it first maps the structure read-only and marks structural repetition, then edits line by line section by section, and finishes with the repository's punctuation checker.

### /read selects a fetch method by domain

`/read` routes by domain: Feishu and Lark use the Feishu API script; WeChat articles try the proxy cascade first and use the built-in WeChat script only after all proxies fail; remote and local PDFs use the PDF extraction pipeline; GitHub URLs prefer raw content or the `gh` CLI, with proxy cascading as a fallback; all other web pages run `scripts/fetch.sh`, use the proxy cascade, and fall back to Markdown only.

The proxy cascade follows a privacy-first order: try local extraction first, then consider sending a public URL to defuddle.md or r.jina.ai. Authenticated or sensitive URLs are never sent to third-party proxies.

The output format is fixed: title, author if available, source platform, original URL, a three-to-five-sentence summary, and full Markdown. Content over 200 lines is truncated with an explanation. By default, save to `~/Downloads/{title}.md` with YAML frontmatter, unless the user says to preview only or not to save. After saving, report the path and stop. Analyze or comment only when asked.

### /health audits engineering health in layers

`/health` performs a budget-aware engineering health audit across five layers: agent configuration, instruction surface, tools and runtime, validators, and maintainability. It finds violations, identifies layer mismatches, and calibrates depth to project complexity.

The report separates agent-configuration risk from AI-maintainability risk. Each finding names the mismatched layer, specific evidence, and a copyable action or diagnostic command. Evidence can come from health scripts, tracked project instructions, runtime configuration summaries, validator logs, hooks and MCP surfaces, and, when needed, live probes.

The report has two parallel tracks. Agent configuration health covers instruction drift, permissions, hooks, MCP, skills, and the memory supply chain for Codex, Claude, and Pi. AI maintainability health covers project-context surfaces, validator wrappers, generated-artifact checks, ownership hotspots, and stale or misleading persistent docs.

It defaults to a summary audit. It escalates when the user explicitly requests a deep or complete audit; mentions AI code rot, configuration drift, missing validation, or stale validator output; the project complexity is Complex; or the summary exposes a critical ambiguity that cannot be resolved locally. It tells the user before escalating because a deep audit may use more token budget.

### /learn organizes research and writing in six phases

`/learn` has six phases: collect, digest, outline, fill gaps, polish, and self-review and publish. The selected mode determines where the workflow starts and stops.

- **Deep Research** starts at phase 1 and ends at phase 6. Its goal is to understand a field well enough to write an article.
- **Quick Reference** starts and ends at phase 2, producing notes for a fast, usable mental model.
- **Write to Learn** starts at phase 3 and ends at phase 6. It fits material already in hand when writing is used to force understanding.
