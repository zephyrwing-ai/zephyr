## 把 AI 当作合作伙伴

[How to Be More Ambitious: A Tutorial for Humans with Models](https://felixrieseberg.com/how-to-be-more-ambitious-a-tutorial-for-humans-with-models/) 展示了一种与 AI 合作的思维方式：把 AI 当作合作伙伴，而不是简单工具。给它一个看起来不可能完成的目标，把结果标准具体化，让它用专业人士的思维来思考，也借此扩展自己的知识领域。

## Waza 的工程经验

[tw93/Waza](https://github.com/tw93/Waza) 是 tw93 的工程经验项目。

### /think 先给立场，再写代码

`/think` 的第一条约束是：用户批准前不写代码。它要求 AI 直接给出立场，并说明什么证据会让它改变判断，也要求避开“这很有趣”这类回避判断的说法。

它产出 Outcome Contract，也就是结果约定。目标、成功标准、约束、选定方案、拒绝的取舍、测试和交接步骤都要具体到可以直接执行，不留下需要再次决策的部分。

它还有 Durable Context Preflight。在输出计划前，只读取与问题匹配的领域规则，不加载整个规则树。如果计划与项目硬性规则冲突，AI 要用一句话指出冲突的规则、计划中的步骤和建议解法，不能悄悄覆盖规则。规则直接阻断计划时，AI 要停下来询问用户。

`/think` 有三种模式：

- **Lightweight Mode** 用 2 到 3 句话给出推荐修复，列出涉及文件和一项风险，然后等待批准。发现三个以上真正不同且有实质取舍的方案时，自动升级到完整模式。
- **Evaluation Mode** 处理“值不值得”或“该不该保留”这类单一价值判断。
- **Triage Mode** 处理一揽子独立请求或多张截图，用逐项表格输出判断，不把它们合并成一个结论。

### /design 把设计方向说具体

`/design` 的第一条规则是：如果默认提示词就能生成这个结果，设计还不够具体。

写代码前，AI 要直接询问五件事：谁会在什么场景下使用；精确的美学方向是什么，例如“密集编辑风、原生终端、纸上墨迹、粗野主义网格、温暖模拟”，而不是“简洁现代”；用户会记住的一件事是什么，例如字体、色彩系统、意外动效或非对称布局；硬性约束有哪些，例如框架、包体积、最低对比度和键盘可访问性；标志性微交互是什么，例如按压缩放、交错揭示或上下文图标动画，并说明具体实现方式。五个问题全部回答前，AI 不继续。

用户给出 Linear、Claude.ai 或 Vercel 等参考站点时，AI 不能只沿用品牌名，而要提取三个具体属性：按钮圆角的处理方式、表面深度的处理方式，例如阴影、背景色阶或边框，以及强调色所属的色系。

随后，AI 要用三行概括方向：视觉命题，说明情绪、材质和能量；内容计划，按 hero、支撑内容、细节和最终 CTA 展开，每行一句；交互命题，提出 2 到 3 个能改变页面感受的具体动效。生产级或多页面 UI 再扩展为九节 `DESIGN.md` 脚手架，覆盖主题、调色板、排版、组件、布局、深度、do/don't、响应式和提示指南。

不可协商的约束来自已经加载的参考文件，包括排版、OKLCH 色彩、动效时序、布局默认值、CSS 模式禁令、可访问性基线和复杂度匹配。AI 执行这些规则，但不在主指令中重复整套规则。

### /ui 用截图驱动界面调整

`/ui` 用于已有界面出现视觉问题时进行截图驱动迭代。它会保留用户原话中的“丑、乱、不清晰、怪”等诊断标签，不把它们改写成含糊的“现代化”。

它维护一份 Reflex Fonts to Reject 名单，包括 Inter、DM Sans 等字体。禁用的是把这些字体反射性地用作展示字体；如果密集数据表等具体产品界面有合理依据，仍可以使用 Inter。它还包含 CSS 模式禁令、动画标准、色彩系统和主题风格等细则。

规则禁止使用一些 CSS 模式，并规定动效、色彩系统和主题风格。`/ui` 输出禁止使用 U+2014 长破折号，改用逗号、冒号或句号。没有参考时才考虑默认调色板、默认字体和手绘图形。颜色、字体、宽度和语气优先取自当前产品的令牌、相邻组件、截图与 git 历史，其次参考同团队已发布的其他产品。

基于状态切换子元素的容器，例如状态栏、操作栏、工具栏行和菜单项，在所有状态下使用统一字号。状态通过填充、描边、透明度、颜色或图标区分，不用字号变化表达状态。

### /check 把审查和写入权限分开

`/check` 把审查请求与写入权限分开。只读请求可以检查工作区和远程状态；编辑文件、自动修复、提交、推送、发布、评论、关闭、合并或切换分支都需要当前请求中的明确授权，或者来自同一未完成任务且仍然有效的授权。

同一任务里的“继续”不会撤销授权，也不需要重复授权。新动作、扩大范围、改变目标或增加原授权未覆盖的风险，需要新的授权。批准草稿不代表批准提交、推送、发布或删除。

它产出 Outcome Contract。审查结论、发布决定和维护者动作都要根据当前 diff、项目上下文和实时证据。发现、修复、已发布状态或阻塞项，都要附上可证明它们的命令、工件或远程状态。证据可以来自工作区状态、diff、公开项目文档、清单文件、CI、包内容、发布或注册表状态，以及当前命令输出。

多步骤或发布操作，以及包含多个条目或截图的请求，最后都要用编号账目收尾，分别列出已完成、不适用和剩余事项。

审查前先运行 `git status --short --branch -uall`。检查工作区漂移是否让计划变得不安全，指出冲突并停止，然后再执行和运行项目验证命令。

### /hunt 先用证据找到根因

`/hunt` 的硬性规则是：能用一句话说出根因之前，不改代码。根因说明采用“我认为根因是 [X]，因为 [证据]”的格式，并指明具体文件、函数、行或条件。“状态管理问题”不可检验；“`src/hooks/user.ts:42` 中 `useUser` 的缓存过期，因为依赖数组缺少 `userId`”可以检验。

它用诊断信号判断调查是否前进：日志行是否符合假设；是否能在运行前预测下一个错误；是否理解根因到症状的传播路径；是否能写出一个在旧代码上失败的测试。每出现一个信号，都要再找一条独立证据，才能据此行动。

提出假设前，先列出所有可观察症状。假设必须解释每一个症状，只覆盖部分症状的假设仍然是症状级猜测。对于闪烁、间歇性失败和竞态条件等时序问题，先可靠复现再诊断。

它会拦截五种合理化说法：“我就试试”意味着先写出假设；“我很确定”意味着运行能够证明判断的工具；“大概是同一个问题”意味着从头重读执行路径；“在我机器上是好的”意味着枚举环境差异；“再重启一次”意味着逐字阅读最后的错误，没有新证据时重启不超过两次。

修复后同一症状仍然存在时，立即停止。“让我试试这个”也会触发停止。两者都说明假设还没有完成，需要从头重读执行路径。

### /write 保留作者声音，优先做减法

`/write` 的立场是：不要表演词汇上的“改进”。它提供一份气味目录，不是从上到下执行的检查清单。参考文件很长，是因为积累了大量例子；应用更多规则不等于做得更好。

过度编辑和编辑不足一样糟糕。句子已经自然、清楚、稳定时就保留。润色大多是减法，删除重复、总结腔和重述结论，而不是逐词替换。保留作者原有的口语词、节奏、知识和判断。作者的情绪、立场和有意的文体选择优先于单条规则，例如叙事文章中的问句标题、作者想保留的列表。如果一个表达在上下文中读起来自然，即使它出现在禁用短语列表或替换表里，也要保留。匹配气味，不匹配字符串。少量真正重要的编辑，胜过大量会压平作者声音的机械替换。

开始前先做 Pre-flight：如果用户只给了指令，没有提供正文，用一句话请用户给出文本；然后定位文本、确认受众，最后确定语言。长文先只读映射结构，标记跨段重复、表格复读和冗余段落，再逐节做行级编辑，最后运行标点检查脚本。保留前置信息、代码、媒体、链接和实质说明。

禁用词和替换表是例子，不是查找替换。先看上下文，判断作者有意的表达和套话，再决定是否修改。三处真正重要的改动胜过三十处机械替换。

### /read 按域名选择抓取方法

`/read` 根据输入域名选择抓取方式：飞书和 Lark 使用飞书 API 脚本；微信公众号优先使用代理级联，全部代理失败后才使用内置微信文章脚本；远程 PDF 和本地 PDF 路径使用 PDF 提取管线；GitHub URL 优先使用原始内容或 `gh` CLI，代理级联作为回退；其他网页运行 `scripts/fetch.sh`，执行代理级联，并以 Markdown 作为回退格式。

代理级联遵循隐私优先顺序：先在本地尝试提取，再考虑把公开 URL 发送给 defuddle.md 或 r.jina.ai。需要认证或敏感的 URL 不发送给第三方代理。

输出固定包含标题、作者（如有）、来源平台、原始 URL、3 到 5 句摘要和完整 Markdown。正文超过 200 行时截断并说明。默认保存到 `~/Downloads/{title}.md` 并附 YAML frontmatter，除非用户要求只预览或不保存。保存后报告路径并停止，用户要求时再分析或评论。

### /health 分层审计工程健康度

`/health` 从五个层次开展预算感知的工程健康审计：Agent 配置、指令面、工具与运行时、验证器、可维护性。它识别违规项、层次错位，并根据项目复杂度调整检查深度。

健康报告把 Agent 配置风险与 AI 可维护性风险分开。每个发现都说明错位层次、具体证据，以及可复制粘贴的动作或诊断命令。证据可以来自健康脚本、受跟踪的项目指令、运行时配置摘要、验证器日志、hooks/MCP 表面，以及必要时的实时探针。

报告包含两条并行轨道。Agent 配置健康检查 Codex、Claude、Pi 的指令漂移、权限、hooks、MCP、技能和记忆供应链。AI 可维护性健康检查项目上下文表面、验证器包装、生成工件检查、热点所有权，以及陈旧或误导性的持久文档。

默认从摘要审计开始。用户明确要求完整深入审计、提到 AI 代码腐化或配置漂移等问题、验证缺失或陈旧，项目复杂度为 Complex，或者摘要审计暴露关键歧义且本地无法解决时，再升级为深度审计。深度审计可能消耗更多 token 配额，升级前先告知用户。

### /learn 用六个阶段组织研究与写作

`/learn` 包含六个阶段：收集、消化、列提纲、补全、打磨、自审与发布。模式决定工作流的入口和出口。

- **Deep Research** 从阶段 1 开始，到阶段 6 结束，目标是理解一个领域并写成文章。
- **Quick Reference** 从阶段 2 开始，也在阶段 2 结束，只产出笔记，目标是快速建立可用的心智模型。
- **Write to Learn** 从阶段 3 开始，到阶段 6 结束，适用于已有材料并希望通过写作加深理解的情况。
